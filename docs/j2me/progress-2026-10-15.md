## 根因

HEAD 上让 AMS 起不来的是 **`dc3344530`（9 月 9 日，Fix native S60 phone shell startup）对
`process_command_line` 的修改**。它在 `21efc5f28` **之后**，所以二分时 `21efc5f28` 失败另有原因，**尚未定位**
（`21efc5f28` 里命令行还是旧的截断实现）。见下文第 5 条和“未解决”。

1. **命令行长度单位**。EKA2 euser 的 `RProcess::CommandLine` / `User::CommandLine` 把 `TDes16` 包成
   `TPtr8` 调 Exec，再把返回长度 `>>1`。
   - 旧实现（`9313207a7` 为 J9 引入）按 UTF-16 字符数写长度，guest 实际只看到**前一半**：
     `" -proxy -boot"` → `" -prox"`。
   - `dc3344530` 改成按字节写。这是对的，phone shell 需要完整命令行。
2. **AMS core 以前是“碰巧”能用**。`midp2systemamsv1_5.dll` 的参数解析（`+0xAA0`）只认
   `-config` / `-end` / `-boot` / `-sync` / `-vm`，`-boot` 写 `this+0xCC`。被截断时 core 不认识 `-boot`，
   按普通模式启动 → 向 trader 发 `Private` opcode 1 → 挂出服务器常驻。
   命令行完整后 core 真的进入 `-boot` 模式：跑完 4 个 boot 步骤后（RunL `+0x894`），
   若没有客户端引用（`this+0xFC` 计数为 0，由 `+0x8608` 的 AddRef 递增）就向 trader 发 opcode 2 并从
   `E32Main` 返回。**这是设计行为**（开机跑完 preinstall 后空闲退出），不是崩溃。
3. **host 侧放大了问题**。`interface.cpp` 的 `boot_java_runtime()` 找不到活着的 `-boot` core 就再 spawn
   一个 `" -boot"`，每个都立刻空闲退出，几十个进程堆积，`!MIDP.SystemAMS.MIDP2` 永远不出现。
4. **J9 同样依赖旧的截断行为**。命令行完整时 J9 多走一次 `getEncoding`（`g_j9_encoding_n` 变 4），
   `libmanager.cpp` 里按次数调好的 hook 链走错分支（`conv-ac-unwind`），Main 线程在
   `j9vmall23.dll+0x4ED8C` 读 `0x3` 访问违例，随后页面卡死。
5. `21efc5f28` 同步 yeatse 时删掉了 `featmgr.cpp` 里的 `feature_id_java_midp20`（12），
   SystemAMSCore 启动第一件事就查它。已补回，恢复作者原意。但**实测它不是必需的**：
   HEAD + 下面另外两处改动、临时去掉 feature 12，AMS 照样起来、J9 照样跑。

## 未解决

- `21efc5f28` 为什么失败。那时命令行仍被截断，core 应当以普通模式常驻，feature 12 又已证明不是必需的。
  可能是该提交里别的改动让第一个 core 退出，而本次 `interface.cpp` 的改动（core 退出后由 host 补一个
  普通模式 core）把它掩盖了。要确认需单独构建 `21efc5f28`（worktree + 非 LTO，约 40 分钟）并加探针。
